# DemoFactory MES：barcode 導入評估（草稿，先討論再定案）

建立：2026-10-11 PT · 依今晚對話（Ken 要求評估 barcode 是否能解決品檢/出貨「忘記更新」問題）

## 核心判斷

barcode 解決的是「輸入成本」，不是「意願」。

- 掃碼 ~1 秒 vs 手動打字/找單據 ~10–30 秒。**掃碼變成更新動作本身**（scan = update），才是它讓人願意用的機制。
- 如果掃完還要手動按確認、選工單、填數量，漏更新會原樣回來。設計原則：**掃完即完成，不再多一步**。
- 掃碼無法保證「人會記得掃」——需要一個**強制點**（forcing function）：沒掃就做不了下一步（例如不出掃碼就印不出出貨單、品檢報告結不了案）。

## 1. 掃碼時機（where/when）

| 站點 | 掃碼動作 | 對應的更新 |
|---|---|---|
| 品檢（入料/製程/終檢） | 檢驗員掃工件 label | 該工單的品檢狀態自動更新（合格/不合格＋檢驗員＋時間） |
| 品檢 | 掃 NG label（或量測設備條碼） | NG 數量、原因代碼自動寫入 |
| 出貨（包裝） | 包裝員掃工件 label | 裝箱狀態更新 |
| 出貨（放行） | 掃出貨單上的總條碼 | 出貨確認（日期、數量、客戶）寫入，**沒掃這一步就印不出正式出貨單** |

先從**出貨放行**試行：單點、流程最線性、效果最好量測（漏更新最直觀）。

## 2. 掃什麼（what to encode）

模具業單價高、批量小 → 建議**單件追溯**（每件一 label，終身追溯），這是 barcode 最有價值的場景。

Label 內容（Code128，一維即可，掃描槍最便宜也最耐用）：
```
工單號 | 品號 | 序號/批號 | 數量
例如：WO-20261012-034 | MT-8801-A | S/N 014 | 1 PCS
```
- 出貨總條碼：出貨單號 + 客戶 + 總件數（出貨時列印）。
- 先不要 QR：模具現場油污環境下一維條碼的容錯和掃描速度更好；等需要攜帶量測數據再升級。

## 3. 異常處理（exceptions — 這是 MES 能不能活下來的關鍵）

| 異常 | 設計 |
|---|---|
| Label 損毀/掃不到（油污、刮傷） | 條碼下方印人類可讀編號，允許手動輸入＋標記「手動」，事後可追 |
| 重複掃碼（同一件掃兩次） | 同一工單＋序號 10 分鐘內重掃 → 提示「已掃過」，不重複寫入 |
| 掃錯件（工單 A 的料掃到工單 B） | 掃碼時比對當前工單，品號不符 → 紅燈＋拒絕寫入 |
| 網路/系統離線 | 掃描槍暫存（或手機 App 離線佇列），恢復後自動上傳＋標記延遲筆數 |
| 掃了但沒做（掃完出貨單卻沒出貨） | 出貨確認需「掃總條碼＋司機簽收」兩步才算完成，單掃不算 |

## 4. 硬體與成本（粗估）

- 掃描槍：USB 有線約 NT$1,000–3,000；藍牙約 NT$3,000–6,000。先買 2 支（品檢 1、出貨 1）。
- Label 印表機：Zebra GK420t 等級約 NT$8,000–12,000；耗材每張約 NT$0.5–1。
- 手機替代方案：如果現場已有平板/手機，可先用手機鏡頭掃（慢一點），零硬體成本試行。
- **總試行成本 < NT$20,000**，驗證有效再擴站。

## 5. 建議試行計畫

1. Week 1：只做「出貨放行」掃碼（掃工件＋掃出貨總條碼），量測漏更新率。
2. Week 2：加「品檢」掃碼（合格/NG）。
3. 指標：漏更新件數/總件數、掃碼平均耗時、異常（手動輸入）比例。
4. 試行通過後再做：跨站比對（掃錯件拒絕）、離線佇列。
